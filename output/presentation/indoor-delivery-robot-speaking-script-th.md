# สคริปต์นำเสนอ: ระบบหุ่นยนต์เคลื่อนที่อัตโนมัติสำหรับรับส่งสิ่งของภายในอาคารผ่านเว็บ

สคริปต์ฉบับนี้เป็นฉบับเต็มสำหรับซ้อมนำเสนอหน้า 1 ถึงหน้า 18 โดยส่วนสถาปัตยกรรม ระบบนำทาง เว็บและ Robot Agent และ Mission Flow อธิบายละเอียดกว่าสไลด์อื่น หากต้องนำเสนอภายใน 7 นาที ควรตัดรายละเอียดจากหน้า 6, 9, 10 และ 11 ขณะซ้อมจริง

## หน้า 1 — หน้าปก

สวัสดีครับ วันนี้ผมจะนำเสนอโครงงานเตรียมสหกิจศึกษา เรื่องระบบหุ่นยนต์เคลื่อนที่อัตโนมัติสำหรับรับส่งสิ่งของภายในอาคารผ่านเว็บ

โครงงานนี้เป็นการพัฒนาระบบต้นแบบที่เชื่อมการควบคุมหุ่นยนต์ การสร้างแผนที่ การระบุตำแหน่ง การนำทาง และเว็บแอปพลิเคชันเข้าด้วยกัน เพื่อให้ผู้ใช้งานสามารถสร้างภารกิจและติดตามสถานะหุ่นยนต์จากเว็บได้

## หน้า 2 — ที่มาและความสำคัญ

โครงงานนี้เกิดจากแนวคิดเรื่องการรับส่งสิ่งของภายในอาคาร เช่น สำนักงาน ห้องปฏิบัติการ หรือพื้นที่ที่มีจุดรับและจุดส่งหลายจุด

งานลักษณะนี้อาจเป็นงานที่ต้องทำซ้ำ คนต้องเดินไปรับสิ่งของจากจุดหนึ่งแล้วนำไปยังอีกจุดหนึ่ง หากมีหลายงานเกิดขึ้นต่อเนื่อง ผู้ใช้งานก็ต้องคอยประสานงานและติดตามว่าแต่ละงานดำเนินการถึงขั้นใดแล้ว

ในมุมของระบบหุ่นยนต์ การสั่งให้หุ่นยนต์เคลื่อนที่ไปยังพิกัดสามารถทำได้ด้วยเครื่องมือของ ROS 2 แต่ผู้ใช้ทั่วไปไม่ควรต้องเปิดเครื่องมือสำหรับนักพัฒนาหุ่นยนต์เพื่อสั่งงานทุกครั้ง

จึงเกิดแนวคิดในการพัฒนาระบบต้นแบบที่ให้ผู้ใช้สร้างภารกิจจากหน้าเว็บ เลือกจุดรับและปลายทาง แล้วให้หุ่นยนต์ดำเนินการตามลำดับที่กำหนด ผู้ใช้สามารถติดตามสถานะของงานและดูประวัติย้อนหลังได้จากหน้าเว็บเดียว

## หน้า 3 — แนวคิดการทำงานของต้นแบบ

ภาพนี้แสดงแนวคิดการทำงานของต้นแบบในหนึ่งภารกิจ

เริ่มจากผู้ใช้เลือกสถานีรับสิ่งของและสถานีปลายทาง จากนั้นเว็บสร้างภารกิจและส่งข้อมูลผ่าน Robot Agent

Robot Agent ทำหน้าที่เป็นตัวกลางระหว่างเว็บกับระบบหุ่นยนต์ โดยรับข้อมูลภารกิจจากเว็บ แล้วเรียกใช้ระบบ Nav2 เพื่อให้หุ่นยนต์เคลื่อนที่ไปยังสถานีที่กำหนด

ระหว่างดำเนินงาน ระบบจะส่งสถานะและเหตุการณ์กลับมายังเว็บ เช่น งานอยู่ในคิว หุ่นยนต์กำลังไปยังจุดรับ กำลังไปยังปลายทาง หรือภารกิจเสร็จสิ้นแล้ว

ดังนั้น จุดที่เราต้องการพิสูจน์ไม่ใช่เพียงการที่หุ่นยนต์เดินได้ แต่เป็นการทำให้ผู้ใช้ เว็บ ระบบนำทาง และหุ่นยนต์ เชื่อมต่อกันเป็นกระบวนการเดียว

## หน้า 4 — วัตถุประสงค์

วัตถุประสงค์ของโครงงานแบ่งออกเป็น 5 ส่วน

ส่วนแรก คือพัฒนาฐานหุ่นยนต์เคลื่อนที่แบบ Differential Drive ซึ่งใช้ล้อซ้ายและขวาในการควบคุมทิศทาง

ส่วนที่สอง คือพัฒนาระบบสร้างแผนที่ ระบุตำแหน่ง และนำทางด้วย ROS 2 โดยใช้ SLAM Toolbox, AMCL และ Nav2

ส่วนที่สาม คือพัฒนาเว็บแอปพลิเคชันสำหรับสร้างภารกิจ จัดการคิว ติดตามสถานะ และเรียกดูประวัติการทำงานตามสิทธิ์ของผู้ใช้

ส่วนที่สี่ คือพัฒนา Robot Agent เพื่อเชื่อมต่อระบบเว็บกับระบบหุ่นยนต์ รับส่งคำสั่ง ข้อมูลตำแหน่ง และสถานะการทำงาน

และส่วนสุดท้าย คือทดสอบฟังก์ชันหลักของเว็บ การเคลื่อนที่ของหุ่นยนต์จริง และการทำงานร่วมกันของทุกส่วนในพื้นที่ทดลอง

## หน้า 5 — ขอบเขตของโครงงาน

เพื่อให้ตีความผลการทดสอบได้ถูกต้อง เราจึงกำหนดขอบเขตของต้นแบบไว้อย่างชัดเจน

โครงงานนี้ใช้หุ่นยนต์จริง 1 คัน ทดสอบในพื้นที่ภายในห้อง และกำหนดสถานีบนแผนที่ประมาณ 2 ถึง 4 จุด

สิ่งที่ครอบคลุมคือการสร้างแผนที่ การกำหนดตำแหน่งเริ่มต้น การนำทางไปยังสถานี รวมถึงเว็บสำหรับจัดการผู้ใช้ สถานี ภารกิจ คิว และประวัติ

สำหรับขั้นตอนการวางหรือรับสิ่งของ ในระยะนี้ผู้ใช้จะยืนยันผ่านหน้าเว็บ เพื่อทดสอบลำดับของภารกิจให้ครบ

สิ่งที่ยังไม่ครอบคลุม ได้แก่ โครงสร้างบรรทุกสิ่งของโดยเฉพาะ การทดสอบน้ำหนักบรรทุก ระบบตรวจจับสิ่งของจริง การรับรองความปลอดภัยในพื้นที่ใช้งานทั่วไป และการประเมินความเสถียรระยะยาว

## หน้า 6 — สถาปัตยกรรมระบบ

หน้านี้แสดงสถาปัตยกรรมภาพรวมของระบบ ซึ่งแบ่งออกเป็น 3 ส่วนหลัก ได้แก่ Web System, Onboard Computer หรือ ODROID-C4 และ Robot Hardware

เริ่มจากฝั่ง Web System ผู้ใช้ใช้งานผ่าน Web Application ซึ่งพัฒนาด้วย Next.js และ React หน้าที่ของส่วนนี้คือให้ผู้ใช้สร้างภารกิจ เลือกสถานีรับและปลายทาง ตรวจสอบคิวงาน ติดตามสถานะหุ่นยนต์ และดูประวัติของภารกิจ

เมื่อผู้ใช้สร้างภารกิจ ข้อมูลจะถูกส่งไปยัง Backend ที่พัฒนาด้วย FastAPI โดย Backend มีหน้าที่ตรวจสอบข้อมูล จัดการสถานะของภารกิจ และบันทึกข้อมูลลง PostgreSQL เช่น ข้อมูลผู้ใช้ สถานี ภารกิจ และ Event History

จุดสำคัญคือ Web System ไม่ได้เชื่อมต่อกับ ROS 2 โดยตรง เพราะระบบเว็บกับระบบหุ่นยนต์มีรูปแบบการทำงานต่างกัน เว็บทำงานในลักษณะ API และฐานข้อมูล ขณะที่ ROS 2 ใช้ topic, service และ action สำหรับสื่อสารระหว่าง node

ดังนั้น Robot Agent บน ODROID-C4 จึงทำหน้าที่เป็นตัวกลาง โดยเปิดการเชื่อมต่อแบบ WebSocket ที่ผ่านการยืนยันตัวตนกับ Backend เพื่อรับคำสั่งภารกิจจากเว็บ

เมื่อ Agent ได้รับภารกิจ จะเรียกคำสั่งของ ROS 2 เพื่อส่งเป้าหมายให้ Nav2 จากนั้น Nav2 จะวางแผนเส้นทางและส่งคำสั่งความเร็ว หรือ cmd_vel ลงไปยัง Base Driver

Base Driver จะแปลงคำสั่งความเร็วของหุ่นยนต์เป็นคำสั่งความเร็วของล้อซ้ายและขวา แล้วส่งผ่าน UART ไปยัง ESP32

ESP32 ควบคุม Motor Driver รุ่น TB6612FNG เพื่อขับมอเตอร์ TT ทั้งสองด้าน และอ่านข้อมูลย้อนกลับจาก Encoder รวมถึงข้อมูล IMU จาก MPU6050

ข้อมูล Odometry, pose, สถานะการนำทาง และเหตุการณ์ของภารกิจจะส่งย้อนกลับไปยัง Robot Agent แล้วอัปเดตกลับขึ้น Web System

อีกส่วนหนึ่งคือกล้อง USB ซึ่งส่งภาพเข้าบริการ Camera Service บน ODROID-C4 ก่อนส่งต่อเป็นภาพสดให้ผู้ใช้ดูผ่านเว็บ

สรุปคือ Robot Agent ทำให้เว็บสามารถควบคุมและติดตามหุ่นยนต์ได้ โดยไม่ต้องให้เว็บสั่ง ROS 2 หรือฮาร์ดแวร์โดยตรง

## หน้า 7 — ฐานหุ่นยนต์และ Differential Drive

หุ่นยนต์ต้นแบบใช้ระบบขับเคลื่อนแบบ Differential Drive ซึ่งควบคุมการเคลื่อนที่จากความเร็วของล้อซ้ายและล้อขวา

หากทั้งสองล้อหมุนด้วยความเร็วใกล้เคียงกัน หุ่นยนต์จะเคลื่อนที่เป็นเส้นตรง แต่หากความเร็วต่างกัน หุ่นยนต์จะเลี้ยวหรือหมุนตามความแตกต่างของความเร็วล้อ

ODROID-C4 ใช้เป็นหน่วยประมวลผลหลักสำหรับ ROS 2 ระบบสร้างแผนที่ ระบบระบุตำแหน่ง และ Nav2

ESP32 รับหน้าที่ควบคุมมอเตอร์และอ่านค่า Encoder ของล้อ ขณะที่ LiDAR ใช้สแกนสภาพแวดล้อม IMU ใช้วัดการเคลื่อนที่ และกล้องใช้ส่งภาพสดเข้าสู่ระบบเว็บ

การแยกบทบาทแบบนี้ช่วยให้คอมพิวเตอร์หลักประมวลผลงานที่ซับซ้อน ส่วน ESP32 ตอบสนองกับอุปกรณ์ระดับล่าง เช่น มอเตอร์และ Encoder ได้โดยตรง

## หน้า 8 — ฐานหุ่นยนต์ต้นแบบจริง

หน้านี้จะแสดงรูปของหุ่นยนต์จริงที่ใช้ในการทดลอง โดยในภาพจะเห็นชุดล้อ มอเตอร์ ชุดควบคุม เซนเซอร์ และคอมพิวเตอร์สำหรับประมวลผล

หุ่นยนต์คันนี้เป็นต้นแบบที่ใช้ทดสอบการสร้างแผนที่ การระบุตำแหน่ง และการนำทางภายในพื้นที่ทดลอง

จุดสำคัญคือเราได้ทดสอบกับอุปกรณ์จริง ไม่ได้ทำเฉพาะในโปรแกรมจำลอง แต่ต้องระบุให้ชัดเจนว่าฐานนี้ยังไม่มีโครงสร้างสำหรับบรรทุกสิ่งของโดยเฉพาะ จึงยังไม่ใช่การทดสอบระบบขนส่งสิ่งของจริง

## หน้า 9 — Mapping, Localization and Navigation

สำหรับระบบนำทาง เราแบ่งการทำงานออกเป็น 2 ช่วง คือช่วงสร้างแผนที่ และช่วงใช้งานแผนที่เพื่อระบุตำแหน่งและนำทาง

ช่วงแรกคือ Mapping Mode หุ่นยนต์เคลื่อนที่ภายในพื้นที่ทดลอง ขณะเดียวกัน LiDAR จะสแกนระยะของสิ่งกีดขวางรอบตัวหุ่นยนต์ ส่วน Encoder ของล้อจะส่งข้อมูลการเคลื่อนที่ หรือ Wheel Odometry เข้าสู่ระบบ

SLAM Toolbox รับข้อมูล LiDAR scan และ Odometry มาประมวลผลร่วมกัน เพื่อประมาณตำแหน่งของหุ่นยนต์ระหว่างเคลื่อนที่ และสร้าง occupancy grid map

แผนที่นี้แบ่งพื้นที่ออกเป็นบริเวณที่เป็นสิ่งกีดขวาง พื้นที่ว่าง และพื้นที่ที่ยังไม่ทราบข้อมูล เมื่อสำรวจพื้นที่ได้เพียงพอ ผู้ดูแลสามารถบันทึกแผนที่ออกมาเป็นไฟล์ map และ metadata เพื่อใช้ในภารกิจครั้งต่อไป

หลังจากนั้นเข้าสู่ช่วงที่สอง คือ Localization and Navigation Mode

ระบบจะโหลด Saved Map ผ่าน Map Server เพื่อให้ทุกส่วนในระบบใช้แผนที่เดียวกัน จากนั้น AMCL จะรับข้อมูล LiDAR scan และ Wheel Odometry เพื่อประมาณตำแหน่งปัจจุบันของหุ่นยนต์บนแผนที่ที่บันทึกไว้

ก่อนใช้งาน ผู้ดูแลต้องกำหนด Initial Pose เพื่อบอกระบบว่าหุ่นยนต์เริ่มต้นอยู่บริเวณใดและหันหน้าไปทางใด ถ้า Initial Pose ไม่ถูกต้อง AMCL อาจระบุตำแหน่งคลาดเคลื่อน และ Nav2 อาจวางแผนเส้นทางจากจุดที่ไม่ตรงกับตำแหน่งจริง

เมื่อระบบระบุตำแหน่งได้แล้ว Nav2 จะรับ Navigation Goal จาก Robot Agent แล้ววางแผนเส้นทางจากตำแหน่งปัจจุบันไปยังสถานีปลายทาง

Nav2 มีหน้าที่วางเส้นทางระดับภาพรวม และควบคุมการเคลื่อนที่ระหว่างทาง ก่อนส่ง Velocity Command หรือ cmd_vel ให้ Base Driver

Base Driver ส่งคำสั่งลง ESP32 เพื่อควบคุมมอเตอร์ ขณะที่ Encoder ส่งข้อมูลย้อนกลับเข้ามาเป็น motion feedback เพื่อให้ระบบทราบว่าฐานหุ่นยนต์เคลื่อนที่ตามคำสั่งหรือไม่

สิ่งที่ควรแยกให้ชัดคือ Planned Path เป็นเส้นทางที่ Nav2 วางแผน ไม่ใช่เส้นทางจริงที่หุ่นยนต์เคลื่อนที่ผ่านทั้งหมด และการที่ Nav2 รายงานว่าเป้าหมายสำเร็จ หมายถึงหุ่นยนต์เข้าเงื่อนไขเป้าหมายที่ตั้งไว้ แต่ยังไม่ใช่การพิสูจน์ว่าหุ่นยนต์หยุดตรงจุดแบบไม่มีความคลาดเคลื่อน

## หน้า 10 — เว็บแอปพลิเคชันและ Robot Agent

หน้านี้อธิบายบทบาทของ Web System, Robot Agent และ Robot System ให้เห็นเป็นลำดับการส่งคำสั่งและข้อมูลย้อนกลับ

เริ่มจากฝั่ง Web System ผู้ใช้เลือกสถานีรับและสถานีปลายทาง จากนั้นสร้างภารกิจผ่าน Web Application

Web Application แสดงข้อมูลที่ผู้ใช้ต้องใช้ เช่น คิวงาน สถานะของภารกิจ ตำแหน่งหุ่นยนต์ และประวัติเหตุการณ์ แต่การประมวลผลและการบันทึกข้อมูลจะทำผ่าน Backend และ Database

เมื่อ Backend ตรวจสอบข้อมูลภารกิจแล้ว จะส่ง Mission Command ไปยัง Robot Agent

Robot Agent เป็นตัวกลางที่สำคัญที่สุดของส่วนนี้ เพราะ Agent เข้าใจทั้งรูปแบบข้อมูลจากเว็บและรูปแบบการสื่อสารของ ROS 2

ขั้นแรก Agent รับภารกิจจาก Backend เช่น รหัสภารกิจ สถานีรับ สถานีปลายทาง และสถานะเริ่มต้น

ขั้นต่อมา Agent เรียก Nav2 action เพื่อส่ง Navigation Goal ไปยังระบบ ROS 2 และ Nav2 จะคำนวณเส้นทางจากตำแหน่งปัจจุบันไปยังสถานีเป้าหมาย

เมื่อ Nav2 ทำงาน ระบบจะส่ง cmd_vel ไปยัง Base Driver แล้ว Base Driver ส่งคำสั่งไปยัง ESP32 เพื่อควบคุมมอเตอร์และอ่านค่า Encoder

ในทิศทางย้อนกลับ ESP32 ส่งข้อมูล Encoder และข้อมูลการเคลื่อนที่กลับมา ระบบ ROS 2 ใช้ข้อมูลนี้สร้าง Odometry และติดตามสถานะการนำทาง

Robot Agent รับผลจาก Nav2 เช่น ไปถึงเป้าหมายแล้ว กำลังเคลื่อนที่ หรือเกิดข้อผิดพลาด จากนั้นส่ง Mission State และ Event กลับไปยัง Backend

Backend บันทึกเหตุการณ์เหล่านี้ลงฐานข้อมูล และ Web Application อัปเดตหน้าจอให้ผู้ใช้เห็นสถานะล่าสุด

ดังนั้น ผู้ใช้จึงมองเห็นงานในรูปแบบที่เข้าใจง่าย เช่น กำลังไปจุดรับ รอยืนยันการวาง กำลังส่ง หรือเสร็จสิ้น โดยไม่จำเป็นต้องรู้ชื่อ ROS topic, action หรือรายละเอียดของคำสั่งควบคุมมอเตอร์

## หน้า 11 — ลำดับการทำงานของภารกิจ

หน้านี้แสดง Mission Flow หรือสถานะของภารกิจตั้งแต่เริ่มต้นจนจบ

เมื่อผู้ใช้สร้างงาน ภารกิจจะเข้าสู่สถานะ Queued หมายถึงระบบบันทึกงานแล้วและรอให้หุ่นยนต์รับไปดำเนินการ

เมื่อ Robot Agent รับภารกิจและเริ่มส่งเป้าหมายแรกให้ Nav2 สถานะจะเปลี่ยนเป็น Going to Pickup ซึ่งหมายถึงหุ่นยนต์กำลังเดินทางไปยังจุดรับสิ่งของ

เมื่อหุ่นยนต์ไปถึงจุดรับ ระบบไม่ได้ถือว่าการส่งของเริ่มขึ้นทันที แต่จะเปลี่ยนเป็น Waiting for Loading เพื่อรอให้ผู้ใช้ยืนยันผ่านเว็บว่าได้วางสิ่งของแล้ว

เหตุผลที่ต้องมีสถานะนี้ เพราะต้นแบบยังไม่มีเซนเซอร์ตรวจสอบว่าสิ่งของถูกวางบนหุ่นยนต์จริงหรือไม่ ดังนั้นในระยะนี้จึงใช้การยืนยันผ่านหน้าเว็บแทน

หลังผู้ใช้กดยืนยัน ระบบจะเปลี่ยนเป็น Delivering และ Robot Agent ส่งเป้าหมายที่สองให้ Nav2 เพื่อนำหุ่นยนต์ไปยังสถานีปลายทาง

เมื่อหุ่นยนต์ถึงปลายทาง ระบบจะเข้าสู่สถานะ Waiting for Unloading หรือรอยืนยันการรับสิ่งของ

เมื่อผู้ใช้ยืนยันว่ารับสิ่งของแล้ว ภารกิจจะเปลี่ยนเป็น Completed และปิดงานอย่างสมบูรณ์

นอกจากเส้นทางปกติแล้ว ระบบยังรองรับกรณีสิ้นสุดอื่นด้วย

กรณีแรกคือ Cancelled ซึ่งเกิดขึ้นเมื่อผู้ใช้หรือผู้ดูแลยกเลิกภารกิจก่อนที่หุ่นยนต์เริ่มเดินทาง

อีกกรณีคือ Failed ซึ่งใช้เมื่อระบบนำทางทำงานไม่สำเร็จ เช่น Nav2 ไม่สามารถรับเป้าหมายได้ หรือไม่สามารถนำหุ่นยนต์ไปถึงสถานีตามเงื่อนไขที่กำหนด

ทุกการเปลี่ยนสถานะจะถูกบันทึกเป็น Event History พร้อมเวลาและแหล่งที่มาของเหตุการณ์ เช่น มาจากผู้ใช้ Backend หรือ Robot Agent

ข้อมูลเหล่านี้ช่วยให้ผู้ใช้ติดตามภารกิจได้ และช่วยให้ผู้พัฒนาวิเคราะห์ได้ว่าเมื่อเกิดปัญหา ระบบหยุดอยู่ในขั้นตอนใด

## หน้า 12 — การทดสอบแบ่งเป็น 3 ส่วน

เพื่อไม่ให้ผลการทดสอบปะปนกัน เราแบ่งการทดสอบออกเป็น 3 ส่วน

ส่วนแรกคือ Web Application Test ตรวจว่าหน้าเว็บทำงานถูกต้องตามบทบาทผู้ใช้ รวมถึงการสร้างภารกิจ คิว สถานะ และประวัติ

ส่วนที่สองคือ Robot Test ตรวจการสร้างแผนที่ การเลือกแผนที่ และการกำหนดตำแหน่งเริ่มต้นบนหุ่นยนต์จริง

ส่วนสุดท้ายคือ Integration Test ตรวจเส้นทางของข้อมูลตั้งแต่ผู้ใช้สร้างงานบนเว็บ Robot Agent ส่งคำสั่งไปยัง Nav2 และระบบส่งสถานะกลับมายังเว็บ

ผลในหน้าถัดไปจะแสดงหลักฐานของแต่ละส่วนแยกกัน

## หน้า 13 — Web Application Test: สิทธิ์และหน้าจอผู้ใช้

การทดสอบเว็บส่วนแรกเน้นเรื่องสิทธิ์และหน้าจอผู้ใช้

เราเข้าสู่ระบบด้วยบัญชีที่มีบทบาทต่างกัน แล้วตรวจเมนู แดชบอร์ด แผนที่ และข้อมูลภารกิจที่แต่ละบทบาทเข้าถึงได้

ภาพด้านซ้ายเป็นหน้าผู้ดูแลระบบ ซึ่งสามารถดูสถานะระบบ แผนที่ กล้อง และข้อมูลส่วนกลางที่ใช้จัดการระบบ

ภาพด้านขวาเป็นหน้าผู้ใช้งานทั่วไป ซึ่งเน้นการติดตามภารกิจและข้อมูลที่เกี่ยวข้องกับผู้ใช้คนนั้น

การทดสอบนี้ช่วยยืนยันว่าเว็บไม่ได้แสดงข้อมูลทุกอย่างแบบเดียวกันกับทุกบัญชี และแยกบทบาทของผู้ดูแลกับผู้ใช้งานออกจากกัน

## หน้า 14 — Web Application Test: คิว สถานะ และประวัติ

ส่วนนี้ทดสอบการจัดการภารกิจหลังจากสร้างงานแล้ว

ภาพด้านซ้ายเป็นรายการภารกิจ ซึ่งแสดงคิว เส้นทาง เจ้าของงาน และสถานะล่าสุด เช่น Queued, Waiting, Completed, Failed หรือ Cancelled

ภาพด้านขวาเป็น Event History ของ TASK-288 ซึ่งบันทึกลำดับเหตุการณ์พร้อมเวลาและแหล่งที่มาของการเปลี่ยนสถานะ

ประโยชน์ของ Event History คือเมื่อเกิดปัญหา เราสามารถตรวจสอบได้ว่าภารกิจเปลี่ยนสถานะเมื่อใด และมาจากผู้ใช้ ระบบเว็บ หรือ Robot Agent

จึงช่วยให้การติดตามภารกิจและการวิเคราะห์ปัญหาทำได้ชัดเจนกว่าการดูสถานะล่าสุดเพียงอย่างเดียว

## หน้า 15 — Robot Test: SLAM and Localization

สำหรับการทดสอบหุ่นยนต์จริง เราทดสอบทั้งการสร้างแผนที่และการระบุตำแหน่ง

ภาพด้านซ้ายแสดงหน้า Web Mapping ระหว่างสร้างแผนที่ โดยเว็บรับ occupancy map ที่ ROS 2 เผยแพร่ออกมา และผู้ใช้สามารถควบคุมฐานเพื่อสำรวจพื้นที่ได้

หลังจากบันทึก Map-Test-01 แล้ว ภาพด้านขวาแสดงขั้นตอนเลือกแผนที่ กำหนด Initial Pose และตรวจสอบสถานะของ AMCL

ในกรณีทดสอบนี้ ระบบรายงานว่า Localized และยอมรับ Initial Pose แสดงว่าหุ่นยนต์พร้อมสำหรับขั้นตอนนำทางไปยังสถานี

ผลนี้เป็นหลักฐานว่าเว็บและระบบ ROS 2 แสดงข้อมูลการสร้างแผนที่และ Localization ร่วมกันได้

## หน้า 16 — Integration Test: TASK-288 จากสถานี C ไปสถานี D

กรณีทดสอบการทำงานร่วมกันใช้ภารกิจ TASK-288 จากสถานี C ไปยังสถานี D

เริ่มจากการสร้างภารกิจผ่านเว็บ จากนั้น Robot Agent รับงานและให้ Nav2 นำหุ่นยนต์ไปยังจุดรับ

เมื่อหุ่นยนต์ถึงสถานี C ผู้ใช้ยืนยันผ่านเว็บว่าได้วางสิ่งของแล้ว ระบบจึงส่งภารกิจส่วนถัดไปให้หุ่นยนต์เดินทางไปยังสถานี D

เมื่อหุ่นยนต์ถึงปลายทาง ผู้ใช้ยืนยันการรับสิ่งของ แล้วระบบบันทึกภารกิจเป็น Completed

จาก Event Timeline จะเห็นลำดับเหตุการณ์ตั้งแต่สร้างงาน เวลาไปถึงจุดรับ การยืนยันการวาง ไปถึงปลายทาง และยืนยันการรับ

กรณีนี้ใช้เวลารวม 2 นาที 53 วินาที โดยผลนี้ใช้ยืนยันลำดับการทำงานของ TASK-288 เท่านั้น ไม่ใช่อัตราความสำเร็จรวมของระบบ

## หน้า 17 — สรุปผลการดำเนินโครงงาน

จากการดำเนินโครงงาน เราพัฒนาฐานหุ่นยนต์แบบ Differential Drive ที่ใช้ ODROID-C4 และ ESP32 ร่วมกับระบบ ROS 2

ระบบนำทางใช้ SLAM Toolbox สำหรับสร้างแผนที่ AMCL สำหรับระบุตำแหน่ง และ Nav2 สำหรับการนำทางไปยังสถานี

ในส่วนเว็บ เราพัฒนาด้วย Next.js, FastAPI และ PostgreSQL เพื่อจัดการผู้ใช้ ภารกิจ คิว สถานะ และประวัติ

Robot Agent เชื่อมสองฝั่งเข้าด้วยกัน ทำให้ระบบรับภารกิจจากเว็บ ส่งเป้าหมายไปยังหุ่นยนต์ และส่งสถานะกลับมาให้ผู้ใช้ติดตามได้

ผลการทดสอบเบื้องต้นแสดงว่าเราสามารถสร้างภารกิจ จัดคิว ติดตามสถานะ สร้างแผนที่ กำหนด Initial Pose และบันทึกเหตุการณ์ของ TASK-288 ได้

ข้อจำกัดของงานคือยังไม่มีโครงสร้างบรรทุกสิ่งของ และยังต้องประเมินความเสถียรของระบบจากการทดสอบหลายเส้นทางและหลายสภาพแวดล้อมเพิ่มเติม

## หน้า 18 — แนวทางการดำเนินโครงงานในสถานประกอบการ

โครงงานต้นแบบนี้ทำให้ผมได้ฝึกการทำงานกับระบบจริง ตั้งแต่ฮาร์ดแวร์ ระบบสมองกลฝังตัว ROS 2 เว็บแอปพลิเคชัน ฐานข้อมูล และการสื่อสารระหว่างอุปกรณ์

สำหรับการปฏิบัติงานสหกิจศึกษา ผมได้รับการตอบรับในตำแหน่ง Programmer ที่ APITechSmart Lab ของบริษัท เอ.พี.ไอ.เทค จำกัด

ลักษณะงานของสถานประกอบการเกี่ยวข้องกับเทคโนโลยีอิเล็กทรอนิกส์ยานยนต์ ระบบควบคุม และการวิเคราะห์ข้อมูลยานยนต์

แนวทางงานที่คาดว่าจะเกี่ยวข้อง ได้แก่ การพัฒนาซอฟต์แวร์สำหรับสื่อสารกับอุปกรณ์ การรับและประมวลผลข้อมูลจากเซนเซอร์ การแสดงผลข้อมูล และระบบสนับสนุนการตรวจสอบหรือควบคุมอุปกรณ์

แม้หัวข้อโครงงานในสถานประกอบการจะยังต้องกำหนดร่วมกับพนักงานที่ปรึกษา แต่ประสบการณ์จากโครงงานนี้จะเป็นพื้นฐานสำคัญสำหรับการทำงานด้านซอฟต์แวร์ ระบบสมองกลฝังตัว และ Internet of Things ต่อไป
